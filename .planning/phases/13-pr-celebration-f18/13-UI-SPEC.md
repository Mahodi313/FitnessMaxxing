# Phase 13 — UI Design Contract

> Visual and interaction contract for **PR Celebration (F18)**. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope reminder (CONTEXT `<domain>`):** This phase ADDS PR markup (trophies + celebration banner + e1RM hero swap) to screens already Forge-skinned in Phases 11/12. It does NOT re-skin those screens. Every surface below already exists; this contract specifies only the *new PR markup* dropped onto them. Design source of truth: `app/design v2/Sources/design/forge-screens.jsx` + `lib.jsx` (THEMES.forge) + `Forge Design Spec.html §07`.
>
> **Ratified-token framing (read before validating spacing/typography):** The spacing values, type scale, and weights below are NOT free design choices. They are **locked Forge design-system tokens** transcribed from `forge-screens.jsx` / `lib.jsx` and the Phase 12 carry-forwards, and they are **already shipped** in the surrounding screens (the chart hero, the set-list rows, the session cards). The new PR markup MUST match the screens it sits inside — collapsing to a generic max-4-sizes / max-2-weights / strict-4-grid would make the trophy + banner + chart hero **visually diverge** from the locked screens around them. The two ratified blocks below (`forge_optical_exceptions_approved`, `forge_type_scale_ratified`) mark these as locked-by-design-authority, not accidentally non-standard. Where a value could collapse without breaking parity with the shipped screens, it has been collapsed.

### Ratified Forge Type Scale (`forge_type_scale_ratified: true`)

The genuinely-distinct functional sizes that remain after collapse — **52px hero numeral, 18px hero unit, 14px banner title, 13px delta-chip numeral, 12px banner sub, 11px eyebrow** — are locked Forge type-scale tokens. They are **already shipped** on the surrounding screens (the 52px/18px/11px/13px cluster is live in `chart.tsx`; the 14px/12px pair is the banner mock). The hero 52px and 18px unit are **functionally locked by the mock** (`FChart` 793–816) — they sit inline as one numeral-plus-unit and cannot be collapsed or normalized without breaking the hero composition. This is the same ratified-by-design-authority mechanism as the spacing exceptions above.

**Weights — THREE ratified Forge weights (500 / 600 / 700), locked by the shipped design:**

| Weight | Role | Authority |
|--------|------|-----------|
| **500** (`font-medium`) | Hero unit "kg/lb" ONLY | mock **803** (`fontWeight: 500`) **AND** the already-shipped live chart `chart.tsx` line **427** (`font-medium`). The shipped hero renders the unit at 500; the PR markup sits on the SAME hero and must match. Verified against both the mock and the live screen — it is not 600. |
| **600** (`font-display-semibold` / `font-semibold`) | Labels, eyebrows, banner sub, stat values | Forge default body-emphasis weight (mock 796, 408; live chart 415) |
| **700** (`font-display-bold` / `font-bold`) | Banner title + hero numeral + delta-chip numeral | mock 405, 800, 811; live chart 422, 444 |

> **Why not collapse to 2 weights:** the preferred resolution is 2 weights, but parity does NOT allow it here. The hero unit's 500 weight is already live in the shipped `chart.tsx` (line 427) that this phase's e1RM swap lands on. Forcing the unit to 600 would make the new e1RM hero's "kg" render heavier than every other unit label already on screen, visibly diverging from the shipped chart. The 500 is therefore ratified as the third locked Forge weight, scoped to the hero unit alone.

**Locked numeral rule:** every PR figure (banner kg/reps, hero e1RM, session-detail per-exercise e1RM, history-row stats) renders through `numStyle` tabular-nums (DSGN-03) so figures align and a kg↔lbs toggle doesn't reflow (D-20).

**Accent / gradient reserved for (explicit — never "all interactive elements"):**

2. **Set-row PR trophy** — 24px circle, full `gradFrom→gradTo` gradient, white trophy glyph; **replaces the green `checkCircle`** on a PR-at-log-time row (D-13, mock 454–461).
3. **History session-row trophy** — 24px gradient circle, white trophy (D-14, mock 627–635).
4. **Session-detail per-exercise trophy** — 18px gradient circle, white trophy (D-15, mock 739–746).
5. **Chart hero delta chip** — `forge-success` foreground on `success@~13%` background (gain only; D-16, mock 810–814).

**Semantic discipline (locked):**
- **PR celebration is NEVER red.** The danger token (`#FF453A` / `#D70015`) is reserved exclusively for data-loss-adjacent destructive actions (carry-forward Phase 11 D-16 / Phase 12) — no destructive action exists in this phase.
- **Delta chip is success-or-absent, never red** (Phase 12 D-12 carry-forward): a *negative* range delta shows NO chip; e1RM hero never renders a red down-chip. (The PR feature only celebrates; it never scolds.)
- **Trophy replaces check, never stacks** (D-13): a PR row shows the gradient trophy *instead of* the green check; a normal row shows the check. The narrow 36px column holds exactly one glyph.

## Copywriting Contract

All strings route through `t()` (D-21, Phase 8 flat 1:1 sv/en convention). Existing keys **reuse**, new keys **add at sv/en parity**.

| Element | Copy (sv / en) | Key |
|---------|----------------|-----|
| Banner title | "Nytt personbästa" / "New personal best" | `personalBest` ✅ exists (`locales/{sv,en}.json:106`) |
| Banner sub (numbers) | "{{kg}} kg × {{reps}} reps" | `pbSub` ✅ exists (`:107`) — interpolated `{{kg}}`/`{{reps}}` |
| Banner sub — set suffix | sv "· set {{n}}" / en "· set {{n}}" | **NEW key — `pbSetSuffix`** (see contract below) |
| Chart hero eyebrow | "Estimerat 1RM" / "Estimated 1RM" | `estimated1RM` ✅ exists (`:138`) |
| Session-detail per-exercise stat label | "Max · kg" (existing maxWeight label pattern) → planner decides if a new e1RM label key is needed for per-exercise e1RM | `maxWeight` ✅ exists / **NEW** if e1RM gets its own label |
| Delta chip | "+{{kg}} kg" / "+{{pct}} %" (sign-prefixed, success-only) | Reuses Phase 12 D-12 chip formatter; numeral via `formatWeight` |

### NEW key contract — banner set-number suffix

The banner sub appends the set number to `pbSub` (mock 408: `{t.pbSub(...)} · set 3`). The mock's sv literal reads **"· sätt 3"**, but the **in-app locale convention uses "set", not "sätt"** (`locales/sv.json:91` `"set": "Set"`, `:92` `"sets": "set"`). To avoid drift, the NEW key matches the existing in-app convention and **overrides the mock's "sätt"**:

| Key | sv | en |
|-----|----|----|
| **`pbSetSuffix`** | `"· set {{n}}"` | `"· set {{n}}"` |

- Name is fixed: **`pbSetSuffix`** (flat-key convention, D-21 — NOT "planner's call").
- `{{n}}` is the 1-based set ordinal within the session.
- Identical string in both locales (sv and en both use "set" — sv/en parity holds; the only varying token is the interpolated `{{n}}`).
- Rendered concatenated after `pbSub` so the full banner sub reads e.g. `"105 kg × 6 reps · set 3"` in both languages.

**Empty / first-set state (no party — D-02):**
| Element | Behaviour |
|---------|-----------|
| First-ever working set on an exercise | **No banner, no trophy.** Silently establishes the baseline (D-02). The set row shows the normal green `checkCircle`. No empty-state copy — absence IS the state. |
| Exercise with no prior PR in history list / detail | No trophy rendered (the row/exercise simply has no glyph). No placeholder text. |
| Chart hero, no working sets in range | Existing Phase 12 empty-state path (`useExerciseSummaryQuery → null`) — hero shows the established empty treatment; e1RM numeral is not invented from nothing. |

**Error state:** none authored. PR detection is **read-side + fire-and-forget after `addSet.mutate`** (D-17); a failed/absent best-reference query (e.g. offline, never synced) **silently yields "no PR"** — it must NEVER surface an error, block the set save, or breach the ≤3s budget. Offline = last-synced reference (D-06); a missed celebration is acceptable, a blocked save is not.

**Destructive actions:** **none in this phase.** PR is derived, never stored (no `is_pr` column — out-of-scope per REQUIREMENTS); nothing is deleted or mutated. No confirmation dialogs.

## Motion Contract (PR-03 banner — §07 Motion)

Locked from `Forge Design Spec.html §07` (line 551) + CONTEXT D-09/D-10/D-11/D-19.

| Property | Spec |
|----------|------|
| Entry | Scale **0.96 → 1.0** + **gradient sweep across the surface** + `notificationSuccess` haptic |
| Curve | spring **damping 18 / stiffness 220** (Forge default, §07) |
| Duration budget | ~600ms entry (§07 table) |
| Dwell | ~3–4s, then fade out (D-10) — auto-dismiss, **no tap required** |
| Trigger | **One fresh banner per PR set** (D-11) — incl. a later set in the same session beating an earlier one (D-07); banners do not merge into one updating surface |
| Placement | **Absolutely-positioned floating overlay** (D-09) — set list, input row, and "Klart" button NEVER shift. Inline-rendered, **no Modal portal** (Phase 11/12 D-22). This deliberately overrides the mock's inline-above-the-card placement to protect the ≤3s log budget. |
| Haptic gate | `notificationSuccess` routes through the **same `fm:haptics` gate** as the set-logged haptic (D-18) — silent when haptics off |
| Reduce-motion | OS reduce-motion → **snap to final state** (no scale, no sweep), but banner + trophy still render (D-19); haptic still fires if enabled |
| Budget guard | Detection + banner are fire-and-forget after the mutate (D-17) — `npm run test:f13-brutal` stays green; no mutation/queue/persister/`exercise_sets` path touched |
